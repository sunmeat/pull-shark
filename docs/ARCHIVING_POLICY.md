# Repository Archiving Policy

## Purpose

Archiving should preserve a useful historical record while making it clear that active maintenance has ended.

## When to consider archiving

The maintainer may consider archiving the repository when its purpose is no longer relevant, ongoing maintenance is not practical, or the project has been replaced by a clearly identified successor.

Before archiving, consider whether a smaller maintenance plan or a pointer to a successor project would better serve users.

## Before archiving

- [ ] Review open issues and pull requests and explain what will happen to them.
- [ ] Update the README with the repository's status and any successor or replacement.
- [ ] Record the final notable changes in the changelog.
- [ ] Check that license and security information remain accurate.
- [ ] Preserve useful documentation and avoid deleting history without a clear reason.
- [ ] Communicate the planned change in an issue or other appropriate public channel.

## After archiving

An archived repository should be treated as read-only. Do not imply that bug reports, pull requests, security fixes, or support requests will receive a timely response.

If the repository is reactivated, review its dependencies, workflows, permissions, links, and security guidance before resuming normal contributions.

## Decision

The maintainer is responsible for the final decision and should explain the reason and effective date in the repository README or a final status notice.
