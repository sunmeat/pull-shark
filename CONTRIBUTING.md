## 🇬🇧 English

Welcome to **Pull Shark**! Thanks for taking the time to help improve this project. Contributions of all sizes are appreciated, from fixing a typo to improving documentation or suggesting a thoughtful enhancement.

The goal is simple: make every change clear, useful, respectful, and easy to review.

### 🧭 Before you begin

- **Look around first.** Read the existing documentation and check open issues or pull requests to avoid duplicated work.
- **Keep the scope focused.** One pull request should solve one problem or deliver one coherent improvement.
- **Discuss larger changes early.** For substantial features or structural changes, open an issue first so the direction can be discussed.
- **Be respectful.** Treat contributors and reviewers with patience and kindness. See the [Code of Conduct](CODE_OF_CONDUCT.md) if available in this repository.

### 🛠️ A good contribution, step by step

1. **Choose a task.** Find an open issue or identify a specific improvement.
2. **Create a branch.** Use a descriptive name, such as `docs/update-guide`, `fix/typo`, or `ci/markdown-checks`.
3. **Make the change.** Prefer the smallest complete solution. Keep unrelated edits out of the same pull request.
4. **Check your work.** Review the diff, validate Markdown formatting, and run relevant checks when available.
5. **Commit clearly.** Write a concise message that explains what changed and, where useful, why.
6. **Open a pull request.** Describe the change, its motivation, and any testing or verification performed.
7. **Work through review.** Respond constructively to feedback and update the pull request when needed.

### ✍️ Commit message examples

Make commit messages specific and easy to understand:

- `docs: improve contribution guide`
- `fix: correct broken navigation link`
- `chore: tidy repository metadata`
- `ci: validate markdown files`

These are examples, not a mandatory commit convention.

### 📬 Pull request checklist

Before submitting, please check that:

- [ ] The title clearly describes the change.
- [ ] The description explains the problem and the proposed solution.
- [ ] Related issues are linked when applicable.
- [ ] The change is focused and avoids unrelated formatting churn.
- [ ] Documentation is updated when the behavior or workflow changes.
- [ ] Markdown and links have been checked.
- [ ] Relevant automated checks pass, if the project provides them.
- [ ] Screenshots are included only when they help explain a visual change.
- [ ] No credentials, access tokens, private information, or other secrets are included.

### 🔍 Reviews and collaboration

Reviews help keep the project reliable. Please consider feedback carefully, ask questions when something is unclear, and explain your reasoning when you disagree. Reviewers should focus on the work itself, offer actionable suggestions, and keep discussion welcoming.

Not every suggestion will be accepted, but every contribution deserves a thoughtful look.

### 🐛 Reporting a problem or proposing an idea

When opening an issue, include enough context for someone else to understand and reproduce the situation:

- What did you expect to happen?
- What happened instead?
- What steps reproduce the problem?
- Is there relevant output, a screenshot, or an example?

For feature ideas, explain the use case and the problem the idea would solve. Avoid posting secrets or sensitive personal data. Do not report security vulnerabilities in a public issue; use a private reporting channel if one is configured for the repository.

### 🌱 Small contributions count

You do not need to submit a major feature to make a difference. Clear documentation, a corrected link, a reproducible bug report, a helpful review, or a better example can all make the project easier to use and maintain.

**Thank you for helping Pull Shark grow, one thoughtful contribution at a time.** 🦈

## 🇷🇺 Русская версия

Добро пожаловать в **Pull Shark**! Спасибо, что хотите помочь проекту стать лучше. Мы ценим вклад любого масштаба: от исправления опечатки до улучшения документации или продуманного предложения новой возможности.

Наш принцип прост: каждое изменение должно быть понятным, полезным, уважительным и удобным для проверки.

### 🧭 Перед началом

- **Сначала осмотритесь.** Прочитайте существующую документацию и проверьте открытые issues и pull requests, чтобы не дублировать уже начатую работу.
- **Сохраняйте фокус.** Один pull request должен решать одну задачу или содержать одно логически завершённое улучшение.
- **Обсуждайте крупные изменения заранее.** Если планируется существенная функция или изменение структуры, сначала создайте issue, чтобы согласовать направление работы.
- **Общайтесь уважительно.** Относитесь к участникам и ревьюерам терпеливо и доброжелательно. Ознакомьтесь с [Кодексом поведения](CODE_OF_CONDUCT.md), если этот файл есть в репозитории.

### 🛠️ Как внести вклад

1. **Выберите задачу.** Найдите открытый issue или определите конкретное улучшение.
2. **Создайте ветку.** Используйте понятное название, например `docs/update-guide`, `fix/typo` или `ci/markdown-checks`.
3. **Внесите изменения.** Стремитесь к минимальному, но законченному решению. Не смешивайте в одном pull request несвязанные правки.
4. **Проверьте результат.** Просмотрите diff, проверьте форматирование Markdown и запустите подходящие проверки, если они предусмотрены.
5. **Сделайте понятный коммит.** Кратко опишите, что изменилось и, когда это полезно, зачем.
6. **Создайте pull request.** Объясните суть изменения, причину и выполненные проверки.
7. **Пройдите ревью.** Конструктивно отвечайте на замечания и при необходимости обновляйте pull request.

### ✍️ Примеры сообщений коммитов

Пишите конкретно и понятно:

- `docs: improve contribution guide`
- `fix: correct broken navigation link`
- `chore: tidy repository metadata`
- `ci: validate markdown files`

Это примеры, а не обязательный формат коммитов.

### 📬 Чек-лист перед отправкой pull request

Пожалуйста, убедитесь, что:

- [ ] Заголовок ясно описывает изменение.
- [ ] В описании объяснены проблема и предлагаемое решение.
- [ ] Связанные issues указаны, если это уместно.
- [ ] Изменение сфокусировано и не содержит посторонних массовых правок форматирования.
- [ ] Документация обновлена, если изменились поведение или рабочий процесс.
- [ ] Markdown и ссылки проверены.
- [ ] Подходящие автоматические проверки проходят, если проект их использует.
- [ ] Скриншоты добавлены только тогда, когда помогают объяснить визуальное изменение.
- [ ] В изменениях нет паролей, токенов доступа, личных данных и других секретов.

### 🔍 Ревью и совместная работа

Ревью помогает поддерживать надёжность проекта. Внимательно рассматривайте замечания, задавайте вопросы, если что-то непонятно, и объясняйте свою позицию, если не согласны. Ревьюерам стоит обсуждать прежде всего саму работу, предлагать конкретные улучшения и поддерживать доброжелательную атмосферу.

Не каждое предложение будет принято, но каждый вклад заслуживает внимательного рассмотрения.

### 🐛 Как сообщить о проблеме или предложить идею

Создавая issue, добавьте достаточно контекста, чтобы другой участник мог понять и воспроизвести ситуацию:

- Какого результата вы ожидали?
- Что произошло на самом деле?
- Какие шаги позволяют повторить проблему?
- Есть ли полезный вывод, скриншот или пример?

Для новых идей опишите сценарий использования и проблему, которую решит предложение. Не публикуйте секреты и чувствительные персональные данные. Не сообщайте об уязвимостях безопасности в публичном issue: используйте приватный канал, если он настроен в репозитории.

### 🌱 Важен даже небольшой вклад

Чтобы помочь, не обязательно создавать большую функцию. Понятная документация, исправленная ссылка, хорошо описанная ошибка, полезное ревью или удачный пример делают проект удобнее и надёжнее.

**Спасибо, что помогаете Pull Shark расти, по одному осмысленному вкладу за раз.** 🦈
